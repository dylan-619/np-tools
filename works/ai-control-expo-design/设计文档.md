# NP-Tools AI 辅助工作台设计

版本：v4.0，2026-10-20。当前默认主案例为“三泵集水井液位控制”，固定C、模型、模拟量/PI、北向点表与HMI已实现；实际参数、代码位置与验证见 [三泵案例实施说明](三泵案例实施说明.md)。[三泵原设计](三泵变频液位联动设计.md) 保留设计过程。此前双泵供水和顺控继续可选，旧工程和运行器不迁移、不覆盖。以下双泵章节保留其独立实现说明，不能作为三泵点表或测试依据。

## 产品流程

用户只使用 NP-Tools：载入点表 → 对话整理工艺需求 → 确认方案与参数 → 生成控制程序与北向点表 → 仿真运行 → 同一对话生成 HMI 并进行工艺调试 → 烧录物理设备。实板步骤先展示固件与连接准备，再进入工具已有ST-Link烧录页；软件基础演示无需实板。

OpenCode Server 在本机单独运行，通过回环 HTTP 连接。SDK、案例库、控制程序、工程文件、设备模型和 HMI 均随 NP-Tools 管理。现场不依赖开发机 KZ3 源码目录、实板、烧录器或其他仿真软件。AI 身份为“现场实施协作工程师”，负责工艺设计补全、方案选择、点位核对和逻辑配置。

主案例复用已经验证的固定 C 模板，模型不逐次重写算法。自然语言可调整设备名称和四个时间参数；模板不支持的需求需说明差异，再选择受支持方案。

## 工艺与控制

水源经过双向电动进水阀 XV101 进入清水箱 TK101，再由并联供水泵 P101 / P102 向下游供水。采用经典离散液位与主备联锁，不使用模拟量仪表和 PID。

| KZ3 板载点位 | 工艺含义 |
|---|---|
| DI1、DI2 | 清水箱低位以上、高位到达；true 为开关成立 |
| DI3、DI4 | 水源可用、下游供水需求 |
| DI5、DI6 | P101 独立运行反馈、故障接点 |
| DI7、DI8 | P102 独立运行反馈、故障接点 |
| DI9、DI10 | XV101 开到位、关到位 |
| DI11 | 设备运行许可 |
| DO1、DO2 | P101、P102 启动命令 |
| DO3、DO4 | XV101 开向、关向驱动 |

以上 11DI / 4DO 适配 KZ3 标准板型的 12DI / 8DO。本次由设备模型提供这些输入，未验证真实接线、触点极性或电气保护。

- 点击“投入自动运行”建立自动请求，冷启动不动作。
- 低于低位建立补水请求，高位到达结束补水；水源不可用则关闭进水阀。水源不足是工艺条件，不冒充阀门故障。
- 有供水需求且高于低位时运行一台泵，P101 优先。低位失去立即停泵，已投入的自动控制可在补水恢复后继续供水。
- 主泵故障停机并锁存，备用泵必须等待两泵命令全断、原泵运行反馈消失和切换间隔全部满足。运行反馈未停时始终禁止接替。
- 泵具备启动确认、停止确认和运行反馈丢失检查。各泵独立故障复位，不能清除另一台设备的报警；故障输入仍在或反馈未停时不解除。
- XV101 开关驱动互斥，到位断电；反向从最终全断起等待 2 秒，再核对当前目标；等待不计入行程。限位矛盾、行程超时报警。排除卡涩后单独复位重试。
- 正常停止立即停泵，并在许可与质量正常时受控关阀。立即停止、撤销许可、任一 DI 坏质量撤销全部 DO 并退出自动；恢复后需重新投入。失电不等于阀门已经关闭。
- 停止优先，停止/复位与投入同拍不建立新自动请求。健康设备复位不产生启停副作用。

## 参数与北向契约

| 配置键 | 北向字段 | 默认 | 允许范围 |
|---|---|---:|---:|
| pumpStartTimeoutMs | P_START_MS | 5000ms | 1000–10000ms |
| pumpStopTimeoutMs | P_STOP_MS | 5000ms | 1000–10000ms |
| valveTravelTimeoutMs | V_TRAVEL_MS | 8000ms | 4000–15000ms |
| switchDelayMs | SWITCH_MS | 2000ms | 2000–5000ms |

参数仅在退出自动、泵反馈停止且阀驱动关闭时可写，下次投入快照生效。使用 DataManager 参数 revision 做比较写入，过期修改直接拒绝，不自动重放。

共 42 个北向字段，包含输入、命令输出、自动/设备状态、独立故障、故障原因、四参数、等待时间及两泵累计运行秒数。物理输出只读，不允许 HMI 绕过工艺直接写 DO。设备运行显示使用独立反馈；累计绑定 GOOD 运行反馈。软件进程内 fake EEPROM 验证不代表实板存储验收。

## 工程生成

`resources/engineering/cases/catalog.json` 是前后端共用的案例入口，定义 ID、资源目录、角色绑定、参数范围与名称。当前提供 `water-supply-station` 和原 `two-device-output-sequence`。

1. 限制点表为 `kz3-project-io/v3`、标准板型及完整唯一的当前案例点位；拒绝重复 YAML 键、别名、超深/超大内容、额外功能和不一致北向约束。
2. 原文和输入散列保存到隔离工程；规范化 C 别名时保留用户描述、扩展字段及 `point-role-map.json`，不猜物理来源。
3. 对话每轮附带当前点位、工艺规则、参数范围、完整配置形状和工程 ID/版本，避免历史会话带错版本。资料中的指令不作为系统规则。
4. 只接收完整 schema JSON；校验闭合字段集合、点位、范围、名称及身份。历史模型回复不自动生成新工程。
5. 用户核对方案卡后，工具复制固定 `logic.c` 与 C 测试，通过 SDK 生成工程点表，再执行严格质量、工程审核和执行证据检查。
6. 成功后才发布版本。保留原点表、规范点表、C 源码、案例配置、北向 CSV、README、scene、sidecar、运行器、构建记录与交付哈希清单。

生成和部署失败保留上一成功交付；历史版本可以重新选择与部署。导出 ZIP 包含当前交付和有界事件记录，重新计算清单散列并移除开发机绝对路径。

## 软件设备模型与运行

Rust 管理一个私有 C 运行器，通过严格 JSONL 管道交换数据，不新增对外服务端口。部署前校验交付哈希，运行器握手确认源码、点表与配置身份。命令、参数和工况均有白名单；只允许操作当前 workspaceId / runId。

C 运行器先按上一拍 DO 推进设备模型，再发布 DI 给真实 DataManager / LogicManager 扫描，最后回传北向状态及过程图数据。前端不另写控制状态机。

- 初始水位 15%，阀关闭，泵停止；水源、需求、许可预置有效，仍需点击投入。
- 泵约 600ms 形成运行反馈、约 400ms 停止；阀全行程约 2 秒。
- 水箱百分比仅来自设备模型，生成约 20% / 80% 两个离散开关；控制 C 不读取百分比或模拟量。
- 右侧支持水源、需求、许可、泵故障、阀门卡住及低/正常/高水位。恢复工况不代替设备复位。
- 新场景联调时钟按每扫描 10ms 推进。系统暂停调度时工艺时钟和模型一起暂停，不把主机停顿当成设备超时；记录调度暂停事件。旧顺控场景仍用原有时钟策略。
- 进程/协议异常终止时显示状态不可用，不将缓存状态当作设备仍在运行。软件时间和目标周期均不作为实板硬实时证明。

## HMI 与产品界面

工作台名称为“AI 辅助工作台”，六步为“点位配置、工艺需求、控制程序、仿真运行、工艺调试、烧录物理设备”。主画面使用水源、管道、阀门、水箱与双泵的完整工艺图；显示补水、供水、主备切换、反馈确认、故障隔离和液位。

全局保留一个“软件联调”标识。主体使用设备与工艺语言，避免反复显示“演示”“输出目标”或实现细节。没有压力、流量、能耗和 AI 评分等无来源指标。控制按钮与独立复位在默认 1100×760 窗口可见；参数折叠，原始点表、源码和验证证据在相应步骤查看。

同一对话请求 HMI 时，模型只返回带当前身份的 `np-tools-expo-hmi-request/v1`，工具从可信模板生成场景数据；不执行模型提供的 HTML 或脚本。场景采用已有 `devices / points / commands / parameters / source` 结构，设备绑定与当前 42 个北向字段校验，附加工艺布局 sidecar。

## 实板交付入口

HMI之后新增独立准备页：当前工程与版本、主机检查状态、固件准备/连接/写入校验三阶段、工程导出及烧录入口。无真实记录时显示待准备/待核验，不将软件运行标为实板运行。进入现有烧录页时预选 `kz3_f427_app`，不自动沿用历史HEX；原独立烧录入口维持既有行为。

当前生成的是主机C工程，尚未接通当前工程到ARM HEX的自动构建。实板必须另行构建包含匹配点配置、控制逻辑与运行框架的KZ3 APP HEX；现有烧录器检查地址、目标MCU再执行Write/Verify。地址/MCU一致仍不能证明它就是当前工程，后续需增加工程到固件的身份关联。此步展示设备交付边界，不伪造无板写入进度或成功日志。

## 联调操作与验收

建议现场操作：载入工艺点表，采用默认参数生成 → 部署 → 对话生成 HMI → 投入自动 → 观察补水和主泵供水 → 开启“主供泵故障” → 观察停机和备用接替 → 恢复工况后独立复位 → 设置阀门卡住与低液位，观察行程超时 → 解除卡住并复位 → 正常停止或立即停止。

自动检查：`pnpm test:engineering`、`cargo test --manifest-path src-tauri/Cargo.toml --lib`、`pnpm build`；macOS应用使用 `pnpm tauri build --debug --bundles app`。新工艺的严格 C 扫描包含24场景；设备模型回归另覆盖正常闭环、主备延时、缺水、高位关阀、故障恢复、参数 CAS、模板隔离和协议边界。保留旧案例回归。

已执行范围是本地主机编译、实际 C 扫描、DeepSeek 对话与 macOS 桌面流程。展会电脑与网络条件下的长时间连续排练仍需另做；Windows、ARM、烧录、实际 I/O 和现场验收不在本次通过声明内。
