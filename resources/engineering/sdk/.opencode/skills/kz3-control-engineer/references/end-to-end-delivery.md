# PLC 输入到控制逻辑与 HIL 的交付闭环

## 目标与范围

完整任务是：现场点位及初步目标 → 主动设计控制方案、补全需求并比较必要备选 → 建议采纳与需求冻结 → 完整配置和
逻辑代码 → 安全性/稳定性验证 → HIL 验收准备 → 获授权且具备条件后实测、修复、回归。
案例知识随技能部署，不能要求用户拥有开发者的案例工程才能理解建议。

执行模式取决于原始任务与持续对话，不取决于最后一条消息是否只有点表。完整交付已获授权时，收到
点表、确认建议或补充证据后继续下一阶段，不降级为只写需求，也不反复要求“确认生成”。明确要求只
讨论需求、单独调用需求技能或只做诊断时尊重该范围；仅要求审查技能本身不授权创建实际控制项目。

需求仍有疑问时，先交付可见草案。每条缺口给出首选处理、适用前提、业务影响、备选和验收场景，批量
请用户选择是否采纳；明确项直接继承。物理绑定、安全态、硬保护、PID 整定等事实不能以案例默认值
补齐。未采纳的关键行为建议与证据缺失阻止冻结，不阻止其余需求和测试设计。

没有目标固件工程时，技能仍可完成需求与验收设计；记录平台适配依赖，不能编造 API 或交付声称可运行
的配置。HIL 条件缺失只阻止硬件验证，不阻止已满足条件的配置、代码、主机验证及 HIL 计划交付。

## 完整配置交付

`project_io.yaml` 必须是当前目标生成器可读取的完整项目源，而非片段、伪配置或待用户手工拼接的表。
逐项核对以下内容；不适用项注明理由，不为满足清单新增不存在的 schema 字段：

| 核对范围 | 交付及验证要求 |
| --- | --- |
| 平台与版本 | 项目 ID、实际 board/Profile、扫描周期及功能资源；列出所依赖固件/配置版本或内容摘要，缺失能力单列 |
| 本机及南向点位 | 模块/通道/设备/站号/端口归属、类型、方向、绑定、极性或有效值、单位与量程、质量/失效策略；备用点不成为控制许可 |
| 物理输出 | 每个输出唯一 owner、启动/停止/故障/失联安全行为、真实反馈关系；远端失联时本机安全目标不等于远端已断电 |
| 逻辑资源 | parameter 默认/边界/单位/生效与持久化语义、one-shot command、只读 state、external input 数据源/范围/时效/恢复、独立功能块实例、必要 runtime 声明 |
| 北向接口 | HMI_SHORT_V1 白名单、短名与中文含义、类型/权限/地址/宽度/单位、命令效果及完成判据；不暴露内部临时状态 |
| 有跨设备联动时 | 仅按 PLC 工程师已定架构明确发送方/接收方、初值、数据有效性、时效、断线与恢复行为；不自行添加协议或硬件 |

在隔离目录使用目标生成器生成 `point_config.h/.md`，再核对完整点表与代码接口。交付实际生成的点表
说明或等价可追溯的配置说明，记录生成命令和源版本；不能手写猜地址，也不覆盖活动生成物。
缺少平台必需能力时报告具体适配项，普通项目生成授权不包含修改 board/Profile 或通信底座。

## 必需交付内容

完整新项目必须具有核心四件套 `README.md`、`project_io.yaml`、`logic.c`、`logic_project_test.c`，还必须
包含下列内容。可并入 README 或沿用已有文档，不强制多份同义文件：

1. 点位与配置说明：原始点位到逻辑角色再到北向字段的映射、缩写词典、未用点、依赖与登记/激活状态。
2. 安全性和稳定性报告：真实命令/结果、需求覆盖与反例、未运行项、风险及阻塞；不能只有一个 PASS。
3. HIL 验收计划与记录入口：准备条件、具体注入步骤、测量方法、预期输出/反馈/时限、恢复动作和结果栏。

使用 [交付与 HIL 记录模板](../assets/project-delivery-validation-template.md) 按实际场景裁剪。

正式交付引用必须可移交：输入基线/冻结版本、源码、完整配置和点表说明保存在用户拥有的稳定目录，
使用包内相对路径；不能把验证器会删除的临时目录、开发机私人绝对路径或仅聊天记录当交付依据。
无需另建重复文档，但应保留可重跑命令、工具版本、源文件摘要及失败/未执行结果。验证器默认清理
临时产物；交付点表应在独立受控输出目录重生成并归档，不改活动生成物。

交接还应说明：参数怎么填写/生效/恢复、启停与模式切换、故障复位范围、禁止启动原因怎么看、异常后
如何恢复；已有发布版本需附兼容差异与回退步骤。部署、回退和现场操作是说明，不代表已获执行授权。
调试项逐项列出当前禁用范围、解除条件和验证责任，不能把“软件已交付”写成“所有功能已投用”。
冻结时已有 Given/When/Then 验收条目，生成阶段补齐实现与主机断言，验证阶段填写证据并形成可执行
HIL 计划。每条原需求/已采纳补充应能追溯到配置或实现位置及适用主机/HIL 用例。未覆盖项不得隐去。

## 安全性与稳定性验收

安全审查按 [安全与可靠性审查](safety-reliability-review.md) 执行，额外明确稳定性测试的指标及证据层级：

| 主题 | 主机/静态检查 | 实板或 HIL 判据 |
| --- | --- | --- |
| 扫描与响应 | 无阻塞、递归或无界重试；循环/资源有上界；定时器边界和 tick 回绕 | 测量最大扫描时长/抖动、输入到物理输出与反馈的最坏延迟；预算包含采集、通信、调度及执行器 |
| 长序列与抖动 | 重复启停、模式切换、复位、阈值噪声、质量变化和组合命令；逐扫描检查不变量，记录种子/次数/虚拟时长 | 按批准负载和持续时间运行，记录误启、非预期复位、失联、延迟超限、计数异常及资源趋势 |
| 通信与负载 | 注入失效/陈旧/恢复、慢设备、重复命令；不确定写结果不能无条件自动重发 | 正常及最大配置负载、慢从站/断线、北向突发并发下测量最坏数据年龄与控制延迟；观察远端实际输出 |
| 掉电与存储 | 初值/恢复策略、故障保持、参数边界和非法记录、保存失败路径；适用时用真实管理器测试 | 上电、欠压、写中掉电、通信重连后的输出与恢复；记录运行累计损失及产品寿命依据 |
| 调节与执行器 | PID/分级/互斥等适用结构的限幅、失效与切换不变量 | 实际过程的超调、稳态误差、动作频率、反馈超时；仿真不能代替整定与机械/水力验证 |

数值门限与持续时间在验收前由需求、硬件能力和风险评审确定；技能提供候选及依据，不能编造统一的
“24 小时即可可靠”或毫秒限值。没有依据的指标标为待确定，相关验收不得 PASS。模拟时间推进不等于
真实连续运行时长，平均时延不能代替最大值。所有适用安全不变量必须零违反；统计样本量和覆盖范围
也必须记录。项目主机测试通过不自动证明上述全部审查项通过。

## HIL 执行与结论回填

HIL 计划至少覆盖实际需求涉及的正常启停、复位不误启、模式/owner 切换、反馈超时、互斥负向窗口或
并联容量、模拟量异常、断线与恢复、重启/保持和负载长序列。逐项写 Given/When/Then、物理注入点、
观察点、允许时限、禁止动作、恢复步骤；不适用必须解释。HMI 回读/协议 ACK 不能充当执行器动作证据。

执行前记录固件和配置版本、控制器/模块/传感器版本、接线与极性、工装/仪器、负载、采样条件和
操作者授权。仿真负载、手工拨动反馈、真实执行器应分别标识证据范围。已有内接工装直接从业务注入
开始，不重复要求接线，但仍核对测试前提。危险负载隔离和急停/硬保护由合格人员确认，软件联锁不
替代硬保护；未经明确授权不烧录、不在线发命令、不带动真实负载。

执行结果按仓库约定写入 `docs/verification/` 并从项目交付文档引用；独立部署使用用户指定证据目录。
记录实际值、日志/波形、失败复现、修复版本及受影响回归用例。修复或配置变更后旧通过结果仅适用于
旧版本，不得沿用为新版本证明。继续修复仅限原授权，硬件/平台缺陷需交由对应负责人。

交付结论分别列出：

- `HOST_PASS`：列明实际通过的自动检查与人工审查；仍是 host-only。
- `HIL_PREPARED / 待实板`：验收计划已形成；逐项列明尚缺环境或待执行项，不代表硬件已就绪或通过。
- `HIL_PASS（限定版本与工况）`：适用关键项全部有实际通过证据，失败项关闭，无未决安全阻塞；只对记录的覆盖范围成立。
- `HIL_FAILED / HIL_BLOCKED`：保留失败或阻塞证据，不以主机成功冲抵。

仅需求交付使用 `document-only`。可以报告“软件交付完成，HIL 待执行”，不能报告“设备运行可靠已验收”。
任何状态都不是 IEC、PLCopen、SIL 或硬件认证；对外措辞继续遵循 [标准符合性声明](standards-compliance.md)。
