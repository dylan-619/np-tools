# PLC 风格控制逻辑质量门禁

本门禁定义项目内可自动检查的 `KZ3 PLC_STYLE_V1` 规范。只有严格验证通过时，项目才可声明“符合
KZ3 PLC_STYLE_V1（host-only）”。该声明表示控制逻辑的扫描模型、确定性、安全收敛、可测试性和代码
复杂度满足本项目门禁，不等同于 IEC、PLCopen、SIL、功能安全或第三方产品认证。

## 必须通过的结构门禁

- 实现 `Logic_Init`、`Logic_Scan`、`Logic_Stop`，职责分别为安全初始化、周期扫描和安全停止；
- 每个物理输出只有一个业务 owner，每扫描都能确定性得到最终值；同一输出在 `logic.c` 中最多出现
  2 个 `IO_OUT` 写点（安全初始化/停止与扫描末尾统一提交），不得在分支中散写；
- 扫描顺序固定为：读取输入和 quality → 形成保护/许可 → 消费命令和解决冲突 → 推进状态机/功能块
  → 统一提交输出 → 更新可观测状态；
- 跨扫描业务状态必须位于 `context->state` 或声明式功能块，不得使用可写文件级 `static`；
- 物理输入通过 `IO_IN` 等公开点名读取；external input 按生成契约读取
  `context->input.external.<name>` 强类型样本并检查 quality。除该例外外，不直接访问
  `context->input.board/rtu`；
- 不使用 HAL、RTOS、通信私有接口、动态内存、阻塞等待、递归或无界循环；
- KZ3 实现 PID 时，每回路 KP/KI 采用独立 application parameter 和北向 `float/read_write` 字段，
  `LogicPidInput.use_runtime_gains=true` 且取对应参数；增益变更撤销本回路闭环并要求重新投入，
  不得把未被 PID 消费的影子字段当作可调接口。详细规则见
  [PID 上位机整定契约](pid-online-tuning-contract.md)；
- 时间判断统一使用无符号差值 `(uint32_t)(now - start)`，测试阈值前一拍、到时、后一拍和回绕；
- STOP、FAULT_SAFE、许可丢失、坏质量和非法状态均收敛到冻结需求定义的安全输出；
- 多台设备支持手动时，逐台手动请求与自动请求分域保存；模式选择后再经过本机许可和冻结的共用安全
  保护形成最终输出。自动调度、轮换、顺控、PID 或工艺联停不得在手动模式改写请求或操作其他设备；
- 按冻结的设备 owner 表逐台检查命令、输出、反馈、故障、复位和实际需要的专属参数/计时只有一个
  写入者；公共测量、阈值、PID 和调度只由共享工艺 owner 计算。改变一台设备时不得串改其他设备，
  共用安全保护仅作用于冻结范围；此项须对照原始点表和真实扫描，不能靠静态脚本推断；
- 多设备自动控制逐台选择 `AUTO`，组级自动使能仅作为附加许可；自动候选只能来自选择自动且可用的
  设备。手动运行计入容量/保护但不进入自动候选；候选不足、联动依赖未选自动和模式切换按冻结策略
  收敛，不允许旧自动请求在重入时误启；
- 自动按时运行/停止或定时轮换时，每台参与设备使用独立、可写的运行/停止时长参数与计时状态；
  相同初值不合并 bind。逐台参数非法或调试占位禁用该台自动周期，保护停机不等待运行时长到期；
- 每台受控设备具有独立 one-shot 故障复位；多设备的命令、北向字段与本机软件故障一一对应，
  `SYS_RST` 不得代替逐台复位。测试证明复位本机不清他机、不掩盖仍存在的客观故障，按恢复白名单恢复本机 READY、监督计时和重投许可，不直接写输出、不恢复旧启动，不改模式、参数或 runtime；
- 声明 `PER_DEVICE_FAULT_RESET` 时覆盖 `DEVICE_RESET_OWNERSHIP`、`DEVICE_RESET_ISOLATION`；
  逐台单独复位、双命令同拍、本机客观故障仍在、他机故障保持和无故障幂等均有断言；
- 每台受控设备有独立只读 `*_F_L` 总故障，汇总该设备全部可见故障分项（含硬接历史锁存）；
  项目测试分别注入硬件、软件和并发故障，覆盖复位后硬件仍在及多设备不串扰；
- 每台受控启停设备/开关阀实现并验证适用的启动/开阀、停止/关阀超时。只有独立真实运行反馈且
  仍有运行目标时，才验证确认运行后的滚动反馈丢失，按冻结时限（继电器设备缺省 `5000 ms`）；
  启停及阀行程按单体契约默认表或明确覆盖值核对，只有实际故障 DI 才验证硬接故障。
  只有开、关到位反馈的阀门只做开、关超时。运行丢失不在启动未确认或停止中重复报警；坏质量独立
  安全处置，不等待运行丢失计时。缺物理反馈时报告能力缺口，不用 DO 或模拟状态伪造；
- 设备有真实运行反馈时逐台使用 T05 声明式累计，并发布只读 `*_RT_S`；不得使用 DO 请求、
  一台共用 counter 或项目手写计时替代。反馈非 GOOD、STOP/Reset/FAULT_SAFE 时不得补记空窗，
  运行反馈恢复后按 T05 重新建立基线；
- 每个已声明 runtime 都发布本机清零命令 `*_RT_CLR` 和存储诊断，内部 `clear_pending` 不占北向点位；逐台测试
  pending/持久化完成、运行中继续累计、存储失败与他机隔离。清零和故障复位互不代替，也不改
  控制输出或另一类状态；
- 互斥切换必须有“旧输出已撤销但新输出尚未允许”的负向窗口测试；并联组验证容量与控制权限制，
  不强制所有主备/轮换组采用全关空窗；
- 项目测试覆盖正常、冲突、坏质量、故障、STOP/Reset、时间边界和恢复，不得只覆盖成功路径。
- 声明 `MANUAL_MULTI_DEVICE` 时覆盖 `MANUAL_INDEPENDENCE` 与 `MODE_ISOLATION`，逐台命令后比较全组
  请求/输出快照，并注入同时发生的自动需求、候选、阶段和计时变化；
- 声明 `PER_DEVICE_AUTO` 时覆盖 `AUTO_SELECTION`、`AUTO_POOL_ELIGIBILITY` 与
  `AUTO_MODE_ISOLATION`，逐台切换、混合模式、候选不足、手动容量占用和联动依赖缺席均有真实断言；
- 声明 `TIMED_AUTO_CYCLE` 时覆盖 `CYCLE_PER_DEVICE_PARAMETERS`、`CYCLE_TIME_BOUNDARY`、
  `CYCLE_INSTANCE_ISOLATION`、`CYCLE_PARAMETER_UPDATE`，逐台不同设定和改单台参数的反例均有断言；
- 使用 external input 时追加 `EXTERNAL_INPUT_LIFECYCLE`，通过真实管理器验证 INIT、合法写入、同值
  刷新、STALE 边界、非法写入、断流计数及恢复不误启；
- README 的 `kz3-requirements/v1` 契约已冻结且无未决项；测试中的 `PLC_TEST:` 标签覆盖每个已声明
  场景，测试调用真实项目逻辑并具有可执行断言。
- 北向 `description` 面向现场/HMI，DO 输出、故障复位、总故障使用直白业务名称，不出现软件目标、
  软件请求、软件解读、软件监督、软件故障或故障锁存等实现术语。

## 自动量化指标

严格验证对 `logic.c` 使用下列项目内维护性预算：

| 指标 | `PLC_STYLE_V1` 上限 | 含义 |
| --- | ---: | --- |
| 有效逻辑行 | 2000 | 去除空行和纯注释后的近似规模 |
| 决策点代理值 | 400 | `if/for/while/case`、`&&`、`||`、三元表达式的静态计数 |
| 最大花括号嵌套 | 8 | 控制结构嵌套复杂度的保守代理 |
| 单输出 `IO_OUT` 写点 | 2 | 防止多分支、多 owner 散写 |
| 单函数有效行 | 400 | 防止单一函数承担过多状态和输出职责 |
| 单函数决策点代理值 | 90 | 限制局部路径复杂度，促使拆分可测试子逻辑 |
| 单函数参数数 | 20 | 限制接口宽度；LogicContext 等平台入口仍纳入统计 |

严格门禁还会建立项目内函数调用图并拒绝直接或间接递归。以上函数级预算、递归检查以及文件级预算
共同对应 PLCopen 质量度量中规模、接口与复杂度的工程原则，但不是 PLCopen 认证或形式化调用图证明。

项目测试还必须满足：有效代码不少于 25 行、决策点代理值不少于 3、可识别断言不少于 3 个，包含
Given/When/Then，并调用 `Logic_Init/Scan/Stop` 或真实 DataManager/LogicManager 路径。该下限用于拒绝
空壳测试，不代表充分覆盖率；工程师仍需逐条对照冻结需求和安全不变量。

这些指标是本仓库的静态审查预算，不是 IEC 复杂度认证、MC/DC 覆盖率或功能安全证明。超限时不能通过
严格门禁；应拆分状态计算、统一输出提交或提交人工设计审查，不能仅提高阈值。

## 严格验证

生成或修改项目后必须运行：

```sh
python3 .opencode/skills/kz3-control-engineer/scripts/verify_project.py \
  application/projects/<项目目录> --strict-quality --require-engineering-review --require-execution-evidence
```

报告必须包含文件级与函数级量化结果、测试断言/场景数、北向契约结果、编译/测试结果和 `host-only`
边界。默认模式仅用于兼容
检查历史项目；新生成项目不得以默认模式代替严格门禁。

新交付测试采用 [实际执行证据](execution-evidence.md)，将静态断言位置/场景标签与实际扫描/断言/完成场景计数分开报告。文件级预算修订依据及目标硬限制见 [硬件适配](plc-engineering-design.md)；未放宽函数复杂度、硬件容量或安全要求。
