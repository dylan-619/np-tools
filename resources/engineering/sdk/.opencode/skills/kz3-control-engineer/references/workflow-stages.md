# STM32-Logic 阶段与停止条件

## 状态机

| 阶段 | 入口 | 主要输出 | 出口 |
| --- | --- | --- | --- |
| `DISCOVERY` | 用户给出 PLC 点表/需求或现有项目 | 范围、原方案、已有资料、适用规则 | 独立补全无需工程；生成时再定位目标仓库 |
| `REQUIREMENTS` | 场景范围可识别 | 可见的 DRAFT README、机器需求契约、点位角色映射、未决项、Given/When/Then | `--requirements-only --require-frozen --require-engineering-review` 通过 |
| `FROZEN` | 无阻塞未决项且追溯引用完整 | 带版本的冻结摘要 | AUTO_PROJECT 原始授权有效，或需求专用模式后用户明确要求生成 |
| `GENERATING` | 已确认冻结需求 | 完整配置、项目四件套、点表说明及选择项登记 | 隔离生成、编译契约成立 |
| `VERIFYING` | 项目源完整 | 严格编译、行为测试、安全/稳定性审查与报告 | 实际 host-only 结果、未覆盖项明确 |
| `HIL_PREPARING` | 需求验收场景已确定，可与生成/验证并行完善 | 注入步骤、物理测量与时限、恢复动作、环境缺口 | 计划可执行或精确列出阻塞项；未执行不标通过 |
| `HIL_VALIDATING` | 硬件动作获明确授权、环境及安全前提满足 | 真实测量、失败修复和回归记录 | 限定版本/工况通过，或失败/阻塞证据 |
| `HANDOFF` | 当前授权内工作结束或有明确阻塞 | 文件、版本、配置、主机与 HIL 分层证据和后续动作 | 软件交付和硬件验收分别说明，不混为完成 |

完整交付必读 [端到端交付契约](end-to-end-delivery.md)。HIL 计划是完整项目必需内容，实际硬件运行
仍须授权和条件；不具备条件时交付软件与计划，不假装运行过，也不搁置能完成的软件阶段。

不得把“已有类似案例”或“代码可以编译”当作需求冻结证据。`AUTO_PROJECT` 中，原始实现请求是文件生成
授权，但不是缺失硬件事实的替代证据；只有完整性门禁通过后才能自动进入生成。

机器门禁只能证明字段齐全、类型正确和声明可追溯，不能证明被引用的点表、安全评审或用户决策真实；
冻结前仍要人工对照正文和原始证据。

`REQUIREMENTS` 阶段允许先建立只含 `README.md` 的“需求草案”目录，让用户能直接审阅产物。该目录不得
加入项目选择，也不能包含根据未确认硬件事实生成的可运行 YAML/C。进入 `FROZEN` 后，`AUTO_PROJECT`
直接补齐正式项目四件套；`REQUIREMENTS_ONLY` 则等待用户以后提出生成请求。

## 可以安全采用的仓库默认值

仅在用户未提出不同要求时作为候选并要求在冻结摘要中确认：

- `schema: kz3-project-io/v3`；
- 板型 `kz3_f427_standard`，仅当目标硬件确为本仓库控制器；
- `scan_period_ms: 10`；
- 未用功能保持 `features.pid/counter/retained: false`；
- 物理输出北向字段只读，通过 parameter/command 改变工艺请求；
- 自动控制输入质量非 GOOD 时禁止新的危险输出，具体是立即停止、延时停止还是保持仍须需求确认。

端子、有效电平、安全值、设备站号、串口参数、寄存器、模拟量单位/量程和 PID 参数从来不是可猜测
默认值。

## 应立即停止生成的条件

以下指设计阻塞；已冻结的调试占位禁用行为与纯 HIL 待办按 [完整性门禁](completeness-gate.md) 区分。
不能用“物理事实未知”放行真实动作，也不能要求所有现场整定和寿命试验先完成才写受控禁用的软件。

- 输出安全值或急停/硬保护边界不明；
- 需求使用的业务点不存在，或无法证明应绑定哪个物理点；
- 多模式控制 owner、冲突优先级或故障恢复行为未定；
- 需要 PID 但方向、量程、限幅、采样周期或整定参数未冻结；
- 活动副本存在未同步修改，且用户要求切换活动项目；
- 继续需要修改 board/Profile、协议地址或平台运行时，而用户只授权普通工艺项目生成。

停止时明确说明缺失证据、影响以及用户如何补齐；仍可完成不依赖这些事实的需求整理和测试设计。

## 冻结后的变更

新点表、业务修订或平台能力变化影响已冻结结论时，记录旧/新版本及差异，将受影响需求恢复 DRAFT，
只重新确认改变的业务结果；不沿用旧冻结块假装新需求已确认。内部等价修复无需重问业务，但需回归
受影响场景。代码、参数或配置变化后，旧 PASS 只属于旧版本；重新建立当前版本的证据。
已有项目继续更新原 README，不因状态变 DRAFT 重命名目录或创建第二个事实源。
