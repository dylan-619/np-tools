# PLC 设备单体与共享工艺归属契约

本契约适用于一个控制器管理多台可控设备（泵、风机、搅拌机、格栅、压榨机、阀等）的需求、生成和验证。
先按柜体＋模块＋通道及点位描述识别真实设备；备用点不产生虚构设备。已明确的点位和工艺要求为基线，
以下是未写明边界时的 PLC 工程建议，不得覆盖明文设备关系、硬接线安全或已发布接口。纯采集项目不
凭此规则新增命令、DO/AO 或可写北向点。

## 1. 先定 owner，再设计控制

| 控制对象 | 默认归属 | 审查要点 |
| --- | --- | --- |
| 启/停、开/关及手动请求 | 设备单体 | 操作第 i 台只写第 i 台请求；命令 one-shot，停止优先；不能借自动结果操作其他手动设备 |
| 自动选择、自动请求、可用资格 | 设备单体 | 每台可独立选 AUTO；组使能只作附加许可；仅 AUTO 且可用的设备进入自动候选池 |
| DO/AO 最终输出、反馈和本机许可 | 设备单体/对应通道 | 每路有唯一输出 owner；区分命令、模块回读、真实运行/到位反馈；共享安全许可可在输出末级作用 |
| 启停/开关超时、运行反馈丢失、硬接故障、总故障 | 设备单体 | 先按真实反馈类型判定适用项；本机诊断不复制全组故障 |
| 故障复位 | 设备单体 | 一台的 one-shot 清本机故障并按恢复白名单恢复可用；不直接写输出，不改模式、参数、runtime 或他机状态 |
| 真实运行反馈驱动的运行时间及清零 | 设备单体 | 有 runtime 即逐台发布累计秒数、独立清零命令；清零 pending 仅内部；采集型也适用，不以组累计/组清零代替 |
| 启动次数等其他统计 | 仅明确需要时 | 不因运行时间必备而新增未认证的计数或报表 |
| 周期运行/停止时长、设备专属频率/行程/超时参数 | 设备单体 | 各有 bind、范围、质量/占位和计时实例；改单台参数不得重置他机计时 |
| 液位/压力等公共测量、分段阈值、目标台数、PID 回路、轮换仲裁 | 工艺/设备组 | 共享量只定义一个 owner；调度仅分配给合格 AUTO 单体，不能越过其模式或本机保护 |
| 急停、真实硬保护、共享管路/电气互锁、控制器 STOP | 明确的共享安全范围 | 可跨设备约束最终输出；区分安全约束与普通自动顺控，写出触发、作用对象和恢复 |
| 组级故障、组级命令、共用时长 | 仅明文需要时 | 写明独立用途与作用范围；不能代替逐台模式、复位、总故障或周期参数 |

设备单体不等于完全无联动：手动运行仍占用真实容量和共用资源，也必须服从客观安全保护；自动
联动、轮换、加减设备不能反向改写手动请求。工艺阈值、PID 或共享传感器不因每台能选自动而重复
生成 N 份。下游设备未选自动时，默认阻止依赖它的上游自动启动并报告受阻；若工艺要求明文允许使用
已手动运行的下游作为联动许可，单独冻结可验证的反馈条件、责任边界和失效处理。

### 远程许可不是设备故障

- `GOOD + REM=false` 表示未切到远程/当前不允许本控制器控制：禁止本机手动与自动控制、剔除本机
  自动候选，按许可移交规则撤本控制器输出；不置设备故障、不锁存、不计入 `*_F_L`，也不生成
  `*_F_REM`。首拍未远程、长期未远程、运行中转就地都适用；控制不可用不等于设备有故障。
- 未获许可的命令不排队重放，不启动反馈超时监督。失去远程控制权时，由正常许可/owner 路径取消
  被中止动作的监督；不能因撤远程输出或就地运行反馈仍为 true，新报启动/停止/开关阀超时或运行丢失。
  许可撤销不等于已发出有效停机/关阀动作，更不能宣称就地设备已停；不得越权补发停机或关阀命令。
- 真实硬接故障及已发生的软件故障仍按各自来源保留；远程恢复按既定模式/恢复策略重新评估，不因
  单纯未远程要求故障复位，也不借恢复重放旧启停命令。`REM` 质量非 GOOD 仍按质量/通信安全策略
  处理，不当成可信 false；此规则不取消真实设备故障、坏质量保护或真实 RUN 驱动的运行累计。
- 北向使用已有只读 `*_REM` 表示许可；需要可用状态时复用有用途的 `*_AVL`，不另造重复故障点。
  旧案例把未远程锁存为故障的做法不得继承；已发布字段的删除或语义迁移另做兼容评估，不在技能
  维护中修改现场项目。
- 模板接口也要分域：会把安全许可失效锁存为故障的 `T01.safety_permit`、`T02.global_permit/permit_a/
  permit_b` 不能直接接入普通远程许可。必须在 owner/许可层隔离未远程与动作监督；模板无法完成无
  误报的控制权移交时用 CUSTOM_REVIEW_REQUIRED 适配并测试，不能声称原模板认证覆盖此变体，也
  不能为此删除真实安全保护。

## 2. 需求阶段一次性完成归属审查

对每台真实受控设备建立一行：`设备/角色 → 物理点及反馈 → 手动命令/请求 → AUTO 选择/自动请求
→ 输出 owner → 专属参数/计时/累计 → 硬件和软件故障/总故障 → 本机复位 → 必要北向点 → 验收场景`。
另建共享工艺行：`公共测量/阈值/PID/目标台数/仲裁/联动/安全互锁 → owner → 作用设备 → 失效与恢复`。
逐列标记 `已明确 / 工程建议待确认 / 证据待补 / 不适用`；一台设备没有自动周期，就不要为其
造运行/停止时长。明文要求共享或已发布全局接口与默认逐台规则冲突时保留原文，说明兼容风险和
推荐迁移，不静默覆盖。对用户只提交一张合并建议卡，确认实质业务例外，不逐台追问技术实现。

冻结前反向核对：每个物理受控设备均在表内；每个命令、参数、状态、故障和输出只有一个 owner；
每个共享量都有明确作用范围；每个可写北向点都有真实操作用途。任一缺失或一对多归属不清时保持
DRAFT，不靠命名猜测。新设备或控制关系变化时重做该表，不只补一个点位。

## 3. 生成与验证

按设备实例分离 `manual_request[i]`、`auto_request[i]`、模式、故障、监督计时和必要参数；公共
工艺计算只产生 AUTO 候选/需求，最终输出逐台以唯一 owner 仲裁，并通过本机与共享安全许可。
逐台核对 README、`project_io.yaml`、`logic.c`、生成点表与 HMI 短名/bind 是否同一语义；不得因
“北向最小化”删掉每台必要的模式、命令、总故障或已接线且配置量程的 AI 工程值，也不发布内部临时量。

测试至少选两台不同状态的设备，做 A 动作前后全组快照：单台手动启停、单台切 AUTO、自动需求/计时
变化、单台参数修改、单台故障与复位、同拍多台复位，分别检查 B 的请求、最终输出、模式、参数、
计时和故障不被串改。再单独注入真实共享安全保护，确认其只影响明定范围；测试共享工艺变化只调度
合格 AUTO 设备，并验证手动运行容量、候选不足及联动依赖失效。只用静态关键词或一台正常路径
不能证明隔离；host 测试不能替代 HIL 对真实接线、反馈和安全动作的验收。

## 4. 每台执行设备的通用反馈故障

凡项目控制设备启动/停止或阀门开/关，需求阶段逐台建立“动作输出 → 真实反馈 → 故障 → 处置”表，
手动和自动共用本机客观保护。先核实真实反馈类型，不把四类故障机械套给每台设备：

1. **硬接故障**：仅当该设备有实际接线的故障反馈 DI/已证实等效硬接信号时，`GOOD + 故障有效`
   立即置本机故障锁存，DI 恢复不自动清历史记录；原始 DI 留作判定，不直接充当北向故障记录。
   原始 `*_FLT`、硬接故障记录 `*_F_DEV` 与总故障按下面一致性规则区分。未接故障点时不生成硬接故障，
   不把输出请求、通信错误或软件超时冒充硬接故障。
   远程许可 DI 未成立不属于硬接故障；总故障也不得把 `!REM` 当作软件故障合入。
2. **启动/开阀故障**：从本机启动/开阀动作真正发出起，在已冻结超时时间内等不到 `GOOD + 运行`
   或 `GOOD + 开到位` 才置位；首次反馈确认前不判运行反馈丢失。
3. **停止/关阀故障**：从停止/关阀动作真正发出起，在已冻结超时时间内等不到 `GOOD + 已停`
   （通常为运行反馈 false）或 `GOOD + 关到位` 才置位；撤销 DO 本身不等于设备已停。
4. **运行反馈丢失**：仅有独立、真实的设备运行反馈信号，且本项目已确认运行并仍要求保持运行时监视；
   从首次观测 `GOOD + 非运行` 起建立连续丢失窗口，满本机已冻结时限（继电器设备缺省 `5000 ms`）
   才置位；再获得 `GOOD + 运行`
   立即取消窗口，不能从上一拍运行时间提前起算或累计间断丢失。收到停止请求或保护撤销运行目标后
   退出此窗口，按实际停止动作转入停止超时监督；
   坏质量单独按安全策略处理，不把坏质量或从未启动成功误报为运行丢失。只采集运行反馈、没有
   本机运行命令/目标的项目可累计时间，但不能凭反馈变为 false 就推断“运行丢失”。

只有开到位/关到位反馈的阀门只做开阀超时和关阀超时；这两路到位信号不等于运行反馈，不据此
生成运行反馈丢失、到位反馈丢失或运行时间累计。阀另有真实运行反馈或故障 DI 时，才分别
核对对应功能及证据，不把“只有双到位”的默认扩大。

已有设备/驱动器提供开关超时故障时，核对来源、方向、时间、锁存和复位语义后可复用；只给一个
笼统故障位、无法区分开/关超时的，不能宣称两项已完整覆盖。

### 未指定时的反馈时限默认值

以下为用户已确定的项目族默认规则，需求阶段直接写明沿用，不再次询问数字或是否采纳；不是
IEC/PLCopen 规定的固定时间，也不证明实际设备已通过 HIL。当前明确值、有效冻结契约及设备手册
约束优先；出现实质冲突时说明依据，不静默覆盖。维护技能不回写既有现场项目或认证模板。

| 适用对象 | 监督项 | 默认值 | 起点 |
| --- | --- | --- | --- |
| 直接继电器控制的泵、机器 | 启动反馈超时 | `5 s / 5000 ms` | 本机实际发出有效启动动作 |
| 直接继电器控制的泵、机器 | 停止反馈超时 | `30 s / 30000 ms` | 本机实际发出有效停止动作 |
| 直接继电器控制且有真实 RUN 的泵、机器 | 运行反馈丢失滚动窗口 | `5 s / 5000 ms` | 已确认运行、仍要求运行时首次观测 GOOD 非运行；GOOD 运行取消窗口 |
| 有对应到位反馈的阀门 | 开到位、关到位超时 | 各 `120 s / 120000 ms` | 对应方向有效动作实际发出，逐方向独立计时 |

只给部分时限时，仅对未指定的适用项使用默认；不把变频软启动、厂家内置控制器等其他驱动方式
直接视为继电器设备。逐台在需求正文、配置/常量、实际逻辑和验收用例保持同值、同单位、同起点，
冻结时标记来源为“已定共性默认”，HIL 再校核实际反馈时序。不要因采用默认时限额外发布内部计时点。
普通过程阈值确认和非安全级外部数据有效窗口仍分别默认 `30 s`，不得与反馈时限混用。

软件故障逐设备锁存并由本机 `*_RST` 清除；硬接故障的
客观条件不可清，保护输出及恢复/重启策略按冻结需求，不因定时监督延迟急停或硬保护。
若原需求明确要求某项故障而缺少其必需的硬接、运行或到位反馈，保持需求缺口与 DRAFT；
不能靠编造反馈使其通过。仅有双到位的阀门按上述两项超时验收，不因没有运行/硬接反馈阻塞。

### 故障记录、可见分项与复位一致性

- “复位只清软件故障”指只清本机在软件中保存的故障锁存，包含真实硬接故障触发的历史记录；
  不等于禁止恢复本机阶段或重投许可，也不等于只清超时而永远不能清硬接故障历史。软件不能改写现场 DI、急停或其他客观条件。
- 有真实故障 DI 的执行设备，任一有效扫描观测 `GOOD + 故障有效` 即置位本机记录，不依赖手自动、
  远程许可或启动请求。DI 恢复后仍保留；有效本机 RST 才能清。坏质量不能当作“根因已解除”。
- 新项目分成三层：`*_FLT -> point.<本机故障DI>` 表示当前硬接故障反馈，`*_F_DEV ->
  state.<本机硬接故障锁存>` 表示硬接故障记录，`*_F_L` 表示总故障。有真实故障 DI 的执行设备
  必须有本机硬接故障记录；原始 DI 在上位机需要实时监控/诊断时保留为只读点，不能为减点禁止暴露。
  不需要原始诊断时可仅内部采集，但不能删除硬接故障记录。FLT 和 F_DEV 语义不同，不算重复点；
  短名、bind、说明都要区分，F_DEV 不能混入质量/反馈矛盾等软件原因。纯采集原始 DI 不自动变成执行设备。
- 启动/停止/开关阀超时、运行丢失等已暴露分项分别保留自己的原因锁存，可并发为 true；不能只用
  一个会被后续故障覆盖的 blocked_reason 代替。硬接记录和软件分项分别反映对应原因，不能互相代替。
- `本机 F_L = OR(本机全部可见故障分项，含 F_DEV 和软件分项)`，每一扫描都成立；全部分项 false 时总故障
  必须 false，任一分项 true 时总故障必须 true。总故障是汇总结果，不另建独立粘住的无来源锁存。
  原因已解除但尚未复位时，F_DEV/相应软件分项和总故障都保持，原始 FLT 可随 DI 变 false。原始
  FLT 是实时状态，不参加“报警分项全 false”的 OR 校验，不直接替代 F_DEV。质量、矛盾或其他保护
  若进入总故障，必须通过语义对应的必要分项可见，不能为减点隐藏原因，也不把 !REM、rearm_required
  或阶段号当故障。并发根因均保留，不能由单个原因码覆盖。
- 对每台建立 `故障来源/内部锁存 → 北向分项及 bind → 本机总故障 → 可清条件/RST` 矩阵，覆盖全部
  总故障来源。复位先判根因、质量及冻结可清条件，清本机允许项后同拍重新汇总；活动根因优先，不能
  出现清零一拍后再置位。没有满足条件的项不清，不能只清总故障或只清显示分项；许可不成立不是
  故障，也不单独阻止复位。确有“已停反馈”等复位条件时按本机反馈能力与有效契约，不从案例盲抄。
- 复位按 reset-recovery-contract.md 清本机故障并可恢复 READY、监督计时和重投许可；不直接写输出，不改模式、参数、累计或他机；
  复位本身不启动。既有综合 FLT（例如已交付粗格栅）按有效接口保留；新项目不继承其混合语义。
  既有字段从实时 DI 改为锁存/综合语义属于接口变化，即使名称/地址不变也要记录授权、说明和
  manifest 差异；本次不调整已交付项目。
- 新建/重新冻结有设备总故障的控制项目声明 `DEVICE_FAULT_COHERENCE`，规划
  `FAULT_LATCH_LIFECYCLE`、`FAULT_VISIBLE_COHERENCE`、`FAULT_RESET_COHERENCE`。真实测试必须从
  生成北向点表的 name/bind 读显示值，不只查内部状态；测短暂故障恢复未复位、活动故障+复位、恢复后
  复位、两原因叠加、只解除/清一项、跨设备复位、同拍故障/复位及坏质量。每一步断言总故障与可见
  分项 OR 相等，并证明复位无控制副作用。没有硬接反馈时测适用软件分项，不虚造 DI。
  同时验证 raw FLT 随 DI 恢复、F_DEV 与总故障保持；RST 不改原始 DI，且 F_DEV 与软件分项独立可并发。

这是已确定的工程规则，直接说明采用，不反复提问。锁存默认只保证当前控制运行生命周期内的记录，
不承诺掉电保留、完整事件日志或捕获扫描之间的短脉冲；需要这些能力时核对平台支持与实际采样证据。

## 5. 运行累计与清零成对交付

只有确证的真实运行反馈才用于设备运行累计；到位反馈、DO 请求和模块回读都不能代替。每个
已声明的 `runtime_counters` 均配套本机 `runtime.<name>.clear` one-shot 北向维护命令、只读
`runtime.<name>.seconds`，并按 T05 发布存储 fault/mask/busy 诊断。`clear_pending` 供内部逻辑和测试
检查，不默认对北暴露。
清零与故障复位是两种命令：清零不改设备输出、控制请求、模式或故障；故障复位不清累计。协议写入
ACK 不等于 EEPROM 已完成，以该设备 `clear_pending` 由 true 返回 false 及新累计纪元为完成判据；
运行中清零后累计可能立即增长，不要求 HMI 必须看到精确 0。既有项目新增维护点位时只追加空闲
地址，不改原字段及 runtime 槽位身份；硬件存储可靠性仍需 HIL/产品放行证据。
