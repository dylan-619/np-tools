# 北向 HMI 点表契约

新项目使用 `HMI_SHORT_V1`：北向点表是面向上位机/组态软件的稳定公共接口，采用显式白名单，不是项目
内部变量转储。只有操作、监控、报警、设定和维护确实需要的字段才能进入 `northbound.fields`。

## 暴露白名单

以下是允许选择的类别，不是每台设备必须发布的全集。新项目遵循“最小必要暴露”：先根据 PLC 已明确
的上位机页面、操作、报警和接口消费者建立候选，不从内部变量表反向全量导出。每个北向字段必须能
说明具体用途，以及不发布会影响哪项操作、判断或必要维护；“以后可能有用”“便于看程序”不构成理由。

- 操作命令：启动、停止、复位、确认、清零等 one-shot；
- 可调设定：模式、阈值、时间、数量、给定值等经冻结需求确认的 parameter；
- KZ3 PID 整定：每个实际 PID 回路的 KP、KI 是必需的可写 parameter，不能按“内部参数”裁掉；
- 关键测量：液位、压力、流量、温度、频率等 HMI 实际显示或报警使用的工程量；
- 设备状态：运行、就绪、可用、远程/就地、手动/自动、故障；
- 工艺摘要：当前模式、需求数量、活动设备、步骤摘要、关键报警；
- 维护诊断：只有明确用于维护页面或故障定位且定义了用户动作的字段。

默认不暴露状态机 phase、候选/中间请求、上一拍值、边沿记忆、时间戳、确认中标志、重试计数、排序
临时量、功能块内部状态、无用户动作的调试量，以及表达同一含义的原始值/工程值重复字段。内部变量留在
`state` 或实现中不等于必须北向发布。

每台受控设备都要有自己的只读总故障字段 `<设备>_F_L`，例如
`M1_F_L -> state.total_fault`（仅一台设备时）。多台设备使用各自的总故障 state，不能把同一个
控制器/工艺段总故障绑定给每台设备。总故障 = 该设备全部可见故障分项的 OR，包含硬接故障历史及软件保护
（如启动/停机反馈超时、运行反馈丢失、反馈冲突或已冻结的设备级质量故障）；没有故障反馈 DI 时应记录
“无硬件故障反馈”，不能凭空生成。新项目 `M1_FLT` 表示当前原始 DI（监控需要时只读暴露），
`M1_F_DEV` 表示本机硬接故障记录，DI 恢复未复位时 F_DEV/F_L 均保持而 FLT 可恢复 false。
原始 DI、硬接故障记录和总故障分别绑定，不能为了减点混成一个字段；原始值不替代报警分项。
按 [故障记录与一致性契约](device-ownership-contract.md#故障记录可见分项与复位一致性) 建立来源/分项/
总故障/可清条件矩阵；质量、反馈矛盾等不得成为不可见总故障。实际北向快照每拍验证报警分项
（F_DEV 及软件分项，不含实时 FLT）OR 等于总故障。
有启动/停止或开/关动作的设备，其适用的启动/开阀超时、停止/关阀超时是 HMI 故障定位字段；
只有独立真实运行反馈且有持续运行目标才发布运行反馈丢失，只有实际故障 DI 才发布硬接故障。
只有开、关到位反馈的阀门只需开、关超时分项；无物理来源的故障不得占位造点。
既有设备自带超时故障可在语义完全一致时复用，不能把笼统 `*_FLT` 同时冒充开、关两个分项。
未切远程只表示无控制许可，不是总故障来源。使用只读 `*_REM` 呈现，不新增 `*_F_REM` 或把
`!REM` 绑定/汇入故障点；旧字段按兼容性规则记录待迁移，不将其当作新项目标准组合。

设备有真实运行反馈时，不按设备名称排除，每台必须发布只读 `*_RT_S`，绑定本机
`runtime.<name>.seconds`（`u32`，秒）；只做采集的设备也不例外。它用于 HMI 运行累计及维护，
不属于可裁剪的临时变量。每个 runtime 都必须配套本机可写 one-shot `*_RT_CLR ->
runtime.<name>.clear` 及 T05 所需存储诊断；`clear_pending` 是内部清零过程状态，不新增北向点位。
这是维护操作，不是设备启停或故障复位。只采集项目也按该规则保留清零，不因此新增 DO 或工艺
控制命令。只有开、关到位反馈的阀门不生成运行累计；没有真实运行反馈时不得把 DO 请求时长伪装为该字段。
已发布项目如使用其他累计字段名，先保持名称与地址，至少核对其只读 `u32`、本机 runtime bind 和
语义；新项目使用统一的 `*_RT_S`，不为规范化静默改动现场地址。

已接线并在本项目使用的 AI 仪表，只要配置了工程量程并将采样值换算为液位、压力、流量等工程值，
每路换算后的工程值就是必需的 HMI 测量字段，即使该仪表仅用于监测、不参与自动控制也要发布。
需求表逐路记录“AI 通道 → 仪表 → 原始量/电气量程 → 工程量程与单位 → 换算结果 → 北向短名/bind”；
生成的北向字段使用只读工程值，HMI 直接显示其工程单位。质量无效、量程未配置或换算失败时，应有
有效性/质量语义供 HMI 显示无效，不能将默认 0 或旧值冒充实时工程值。原始电流、原始码和缩放中间值
默认不再额外发布，只有明确的维护页面需要时才作为例外列出。此规则不要求备用 AI 或未配置工程量程的
采集点凭空生成工程值。

## 最小化审查

1. 需求阶段输出推荐的最小点表和排除项，不让用户逐个决定程序内部变量。每个保留字段关联需求及
   实际页面/接口消费者；新项目缺少用途依据的字段默认不进入白名单，已有明确接口要求不得擅删。
2. 内部字段默认排除，例外必须有具体业务依据：如启动等待标志、内部计时剩余、切换候选、复位中间
   标志、排序结果和原始采样值。需要清料阶段显示或维护处置时只发布必要摘要，不导出整套状态机。
3. 检查重复语义：同一物理测量通常只发布所需工程值，不同时发布无用途的原始值、缩放中间值；已有
   模式枚举且消费者能直接使用时，不再仅为方便重复发布 MAN/AUTO 镜像。不同语义不能强行合并，
   输出请求不等于真实运行反馈，数据未知也不等于停止。
4. 不能为减点隐藏必须处理的报警、控制禁止原因、测量无效/离线或命令完成判据；仅保留其必要表达。
   协议已提供可用质量信息时优先复用，不重复造质量点；未提供时按真实平台能力选择必要的有效性表示。
   runtime 清零等需要 pending/存储故障证据的接口仍遵守专项契约，不能当作临时量裁掉。
5. 交付前对照实际生成的北向集合与冻结白名单，列出保留/排除及理由、字段数和兼容性例外。脚本可以
   检查命名、绑定、权限和地址，但不能证明“上位机是否真的需要”；这部分必须逐点语义审查。
6. 对每路已换算的 AI，核对 HMI 工程值字段存在且只读、单位/换算口径与逻辑一致，并核对质量无效时
   不显示成有效的 0；缺一路即不满足北向交付。

本规则只裁剪北向发布。控制所需的内部 state、定时器、去抖、反馈确认和故障锁存仍须保留；减少
北向字段也不等于已经减少南向采集或通信负载，不得顺带删硬件点、控制依赖或保护逻辑。

`external_input` 是例外的功能性写入入口：若项目确实依赖上级周期数据，每项必须按
[外部实时输入契约](external-input-contract.md) 保留唯一、同类型的 `read_write` 字段，即使该值不显示在
HMI 页面也不能裁掉。它不代表允许全量写内部 state 或物理点；有效性、失联和处置只发布用户实际需要
的最小摘要，不默认发布内部时间戳和中断计数。

## 统一缩写命名规则

`HMI_SHORT_V1` 的缩写不是可选风格，而是需求表、`project_io.yaml`、生成点表和最终
交付表共用的公共名称。同一 `bind` 在四处必须逐字一致，不允许需求阶段写中文拼音、
落盘时改成英文全称、交付时又使用另一套缩写。

- `name` 必须匹配 `[A-Z][A-Z0-9_]{0,23}`，最多 24 个 ASCII 字符；
- 必须按 `<对象代号><序号>_<业务语义>[_<限定/单位>]` 组合；系统级字段用 `SYS_`，
  无序号的唯一仪表才可省略序号；
- 对象代号、业务语义和单位必须从本表取值；不得对同一语义混用 `START/STA`、
  `STOP/STP`、`OUT/DO`、`QUAL/QLT/Q` 等同义写法；
- 现有词典无法表达新设备或新语义时，先在本共享词典增加唯一缩写及中文定义，再在
  项目中使用；不得只在单个项目临时造词；
- `description` 必须是非空中文业务说明，面向现场工程师和上位机用户，直接写设备、动作和结果；不得把
  `软件目标`、`软件请求`、`软件解读`、`软件监督`、`软件故障`、`故障锁存` 等实现术语带入节点说明；
- 绑定 BOOL 物理输出的只读字段写成“对象+动作+DO输出”，例如“1号搅拌机运行DO输出”；
  设备复位写“对象故障复位”，系统专属复位写“系统故障复位”；`*_F_L` 写“对象总故障”。内部锁存和故障来源保留在 bind、
  需求故障矩阵及分项故障字段中，不在总览节点名称里解释实现；
- 完整语义保留在 `bind` 和 `description`，不能只看缩写猜含义；
- 名称、类型、访问权限和地址一经发布即视为接口，后续不得静默改名、改址或复用。

新项目运行累计示例：`P1_RT_S -> runtime.p1.seconds`（只读）、`P1_RT_CLR ->
runtime.p1.clear`（读写 one-shot）；`runtime.p1.clear_pending` 仅供内部判断，不分配北向地址。阀门
分项用 `V1_F_OPN/V1_F_CLS`，有真实运行反馈的设备用 `P1_F_STA/P1_F_STP/P1_F_RUN`；
新项目 `*_FLT` 是必要时暴露的实时 DI；`*_F_DEV` 是硬接故障锁存；`*_F_L` 由全部可见报警分项 OR
汇总，不含原始诊断 FLT。既有综合 FLT/实时 FLT 的差异须明记，已交付接口不在本任务中改绑。
保留实时反馈与历史故障的区分，不因字段名一样继承旧综合语义。既有项目的短名/地址先保留，新增字段按
兼容性规则追加，不为了统一后缀静默重命名。

新项目绑定示例（原始 FLT 行仅在实时监控需要时发布；引用地址按项目分配）：

```yaml
- {name: M1_FLT, bind: point.m1_fault, c_type: bool, access: read, description: 中心刮泥机当前硬接故障反馈}
- {name: M1_F_DEV, bind: state.m1_hardware_fault_latched, c_type: bool, access: read, description: 中心刮泥机硬接故障记录}
- {name: M1_F_L, bind: state.m1_total_fault, c_type: bool, access: read, description: 中心刮泥机总故障}
```

示例只说明三层语义，不是完整配置；实际项目须声明对应 point/state、其他适用软件故障及本机 RST。

多设备逐台发布可写 one-shot 复位：`M1_RST -> command.m1_reset_faults`、
`M2_RST -> command.m2_reset_faults`，分别仅清对应设备软件故障；单设备已发布
`command.reset_faults` 可继续绑定本机 `M1_RST`。`SYS_RST` 只在确有系统级可复位软件故障时
发布并限定系统专属范围，不能代替或扇出为各设备复位。既有全局点位需兼容评估，不静默改名、改址
或改变已有命令含义。`*_F_L` 总故障与 `*_RST` 复位分别逐设备对应，不让一条复位清除他机总故障。

每个 KZ3 PID 回路必须发布一对 `float/read_write` 增益字段。单回路可用
`PID_KP -> parameter.pid_kp`、`PID_KI -> parameter.pid_ki`；多回路使用如
`P1_PID_KP/P1_PID_KI` 的稳定前缀并分别绑定本回路参数。说明必须写明对象、增益类型和工程单位。
这两个字段是必要整定接口，不属于可裁剪诊断量；KD 在当前 runtime API 未支持前不作为可写字段发布。
在线修改的退出闭环、校验、重新投入和持久化遵循
[PID 上位机整定契约](pid-online-tuning-contract.md)。

自动按时运行/停止或定时轮换的每台参与设备，默认各发布一对可读写时长参数：`M1_RUN_M/M1_STP_M`、
`M2_RUN_M/M2_STP_M` 等，分别绑定本机参数（如 `parameter.m1_run_min`、`parameter.m1_stop_min`）。
同值初始设置不等于共用 bind；仅 `SYS_RUN_M/SYS_STP_M` 不满足逐台调节。PLC 已明确共享参数或
既有发布接口需要兼容时记录例外和迁移决定，不静默改名/改址。`*_RT_S` 是只读累计真实运行秒数，
不代替可写的本次运行时长。单位若不是分钟，遵循词典另定一致后缀并写明单位，不误用 `_M`。

多设备自动项目按设备分别提供 `M1_AUTO`、`M2_AUTO`（泵为 `P1_AUTO`、`P2_AUTO` 等）模式选择；
新项目默认采用逐设备可读写 BOOL 选择字段，不把选择做成 one-shot 命令。已有逐设备可读写模式枚举
且 HMI 可直接使用时保留原接口，不重复增加 `*_AUTO` 镜像，但须逐设备映射和验证等价的自动选择；
`*_A_ON` 仅在需要区分“选择自动”和“当前自动有效”时作为只读状态，不能代替选择字段。仅一个
`SYS_AUTO` 或 `AUTO_MODE` 不能作为全组各设备的模式接口；组级使能若确有消费者需求，可另设系统
字段，但各设备选择仍必须保留。内部候选列表、排序、计时和请求数组不得因此北向暴露。

需求解析时先建立“中文业务语义 → 统一短名 → bind”映射；生成时只能复用该映射；

## 兼容性与交付

修改已有已发布项目时，先形成“保留 / 弃用 / 新增”差异表。兼容性优先于新命名规范：旧字段默认保留
原名称、类型、权限、地址和顺序；删除、改名、改址、复用或重排必须由用户确认并记录迁移策略。

项目 README 的点表至少包含：短名、中文含义、bind、类型/权限、地址、HMI 页面或用途，并附本项目实际
使用的缩写词典。不得仅交付机器字段名。

完整设备与仪表的可操作性另按 [北向 PLC 使用验收](northbound-plc-acceptance.md) 逐项核对。MODE 枚举可代替多个互斥 AUTO 开关；操作所需的暂停/禁止原因属于必要诊断。
