# STM32-Logic 验证矩阵

完整交付按 [端到端交付契约](end-to-end-delivery.md) 核对配置、安全、稳定性及 HIL 材料。
新建/重新冻结项目的需求与隔离命令必须追加 `--require-engineering-review`；下表基础命令仅描述检查层级。

| 层级 | 建议动作 | 能证明 | 不能证明 |
| --- | --- | --- | --- |
| 需求结构检查 | `verify_project.py --requirements-only` | 需求契约结构、确认项类型、基础场景集合完整 | 正文事实真实、现场安全值正确、需求已冻结 |
| 需求冻结检查 | `verify_project.py --requirements-only --require-frozen` | 版本/项目 ID/证据已填写、确认项全真、无未决项 | 证据内容真实、用户已做业务签核、软件行为正确 |
| 项目隔离检查 | `verify_project.py --strict-quality` | 冻结契约与项目 ID 一致、YAML 可生成、C 严格编译、项目测试通过、场景标签齐全、常见越界接口/递归未出现、文件级与函数级 PLC_STYLE_V1 指标及 HMI_SHORT_V1 北向契约通过 | 活动项目一致性、完整共享回归、需求与测试同源错误、IEC/PLCopen/SIL 认证、实板 |
| 活动项目检查 | `project_configure.py --check` | 项目源、活动副本、生成物和 lock 一致 | 业务行为、硬件 |
| 定向主机测试 | `ctest -R '^application_logic$'` | 当前项目场景在主机运行 | 共享回归、物理 I/O |
| 完整主机回归 | fresh configure/build + CTest + static checks | 当前工作树主机与静态门禁 | ARM 链接、实板 |
| ARM Debug/Release | 批准工具链脚本 | 固件活动路径编译链接与资源门禁 | 烧录、现场动作 |
| 安全/稳定性语义审查 | 需求到禁止动作、实现及断言逐项追溯，长序列/边界/恢复测试 | 实际覆盖的不变量和资源边界 | 脚本没有测试的性质、真实墙钟长稳、物理最大时延 |
| HIL 验收准备 | 版本/前提、注入步骤、测量点、门限、恢复步骤完整 | 计划可执行、环境缺口可定位 | 硬件通过、设备运行可靠性 |
| HIL/现场 | 按 `docs/verification/` 记录 | 已覆盖接线、极性、通信、反馈和故障行为 | 未覆盖工况 |

完整主机回归命令：

```sh
cmake --fresh --preset host-tests
cmake --build --preset host-tests --parallel
ctest --preset host-tests --output-on-failure
sh tests/run_static_checks.sh
```

切换新活动项目可能暴露共享测试与具体点表耦合；这属于真实兼容性问题，不能因为项目自身测试通过而忽略。

认证模板本身由 `standard_*_template` 和 `standard_logic_template_catalog` CTest 持续验证。项目采用模板后
仍需独立验证点位映射、质量策略、参数边界和项目组合逻辑；模板通过不能证明现场接线或具体项目正确。

多设备对照 [PLC 设备单体与共享工艺归属契约](device-ownership-contract.md) 做 A/B 不同状态的跨设备
反例：一台手动命令、模式切换、专属参数变化、故障与复位，不得串改另一台的请求、输出、模式、
计时或故障；公共工艺变化只调度合格 AUTO 设备，真实共享保护仅影响明定范围。逐台正常测试或
`PLC_TEST` 标签齐全不能代替此审查。

开/关双向阀、闸门按 [双向反转保护验收表](control-timing-contract.md#阀门双向反转保护) 逐台、双向
真实扫描：手动未STOP拒令、早到命令不排队、STOP同拍冲突、1999/2000/2001 ms及到时重新发令；
已有自动流程先停再等满2秒并复核当前条件。另测复位/模式/控制器停启不绕过、tick回绕、阀间隔离和
等待不计行程超时。期望的2000 ms独立取自需求，不从被测实现宏推导；HIL量测真实端子全断窗口。

远程许可按设备归属契约做“只禁止控制、不算设备故障”的真实扫描审查：首次/持续未远程、命令被拒绝、
运行中转就地与恢复不新增设备故障/总故障，不间接误报被中止动作超时；真实故障和坏质量分别验证。
这属于语义验收，不是结构脚本已证明的性质；旧项目相反行为列兼容迁移差异，不在诊断中改现场代码。

每台受控设备还要核对其 one-shot 故障复位：只清本机允许复位的软件锁存，仍存在的故障 DI、坏质量、
运行反馈或其他客观条件保持，命令不产生启动请求、不修改 parameter、不清 runtime。多设备分别验证
A 单复位、B 单复位和双复位同拍互不串扰；没有本机软件锁存时，至少验证本机命令幂等且不会误启。

软件锁存包括已解除的硬接故障历史；新控制项目声明 `DEVICE_FAULT_COHERENCE` 三个专项场景，按设备
归属契约从实际北向字段断言每拍总故障等于可见报警分项 OR（含 F_DEV，不含实时 FLT），测根因恢复
未复位、活动/坏质量复位和多原因，同时证明原始 FLT 随 DI 恢复而 F_DEV 保持。

设备有真实运行反馈时，不论有无本机 DO，都核对每台 T05 runtime 的唯一反馈 trigger、
GOOD 质量、只读 `*_RT_S` 和逐台累计/暂停/恢复；16 槽上限与已投产顺序不能因补点而静默越界。
每个已声明 runtime 还要验证本机北向 `*_RT_CLR`、存储诊断、内部 `clear_pending` 清零事务和跨设备
隔离；仅有故障复位或协议 ACK 不算清零完成。所有受控启停设备/开关阀逐台验证适用的启动/开阀、
停止/关阀超时，逐项核对单体契约默认表或明确覆盖值；只有独立真实运行反馈且持续要求运行才验证
首次确认后的滚动反馈丢失（继电器设备未指定时 5 秒），
只有实际故障 DI 才验证硬接故障。只有开、关到位反馈的阀门只验证开、关超时；缺实际反馈时明确记录能力
缺口，不能用模拟的 fault 点证明硬接链路。主机验证状态机，HIL 验证真实接线与动作。

`required_scenarios` 与测试中 `PLC_TEST:` 标签必须一一对应；标签存在只证明可追溯关系，必须同时检查
断言是否真实驱动输入、扫描逻辑并观察输出/状态。测试规模下限不能替代需求覆盖和人工审查。

项目声明 runtime 时，额外对照 `T05_RUNTIME_COUNTER_USAGE` 检查：`logic.c` 没有自建累计器、真实反馈与
命令时长口径没有混淆、clear/pending/存储诊断可观测、名称与顺序的 schema 兼容性已记录。生成和主机
测试只能证明软件累计事务；EEPROM 实装型号、写中掉电、WP/I2C 故障、5 分钟检查点与停机保存的写寿命
仍必须标记“待实板/待产品放行”。

标准声明必须单列：严格模式通过只证明 `KZ3 PLC_STYLE_V1 (host-only)`；IEC 61131-3 与 PLCopen 为工程
对齐，IEC 61131-2、IEC 61508、IEC 62061、SIL 和 MISRA C 未经专项证据不得声明符合。
