# 面向现场需求的工艺方案与水处理边界匹配

## 职责与入口

默认用户不一定具备 PLC 设计经验。点位表及简短目标可以作为控制方案设计的起点，按
[工艺设计与方案选择](engineer-intake.md#工艺设计与方案选择) 主动补全运行、异常和恢复方案。
已有明确方案时保留其有效约束；不完整时主动推荐，存在矛盾时说明后果并提出修订和可行备选。
不能以“只补边界”为由拒绝设计，也不能用案例替换未经用户采纳的重要工艺选择。

读取技能自带的 [水处理边界库](water-process-boundaries/README.md)，按其目录只读取命中的案例卡。
全部路径相对本技能解析，复制完整技能即可携带这些知识。匹配边界、形成需求草案不要求存在 KZ3 工程；
实际生成或编译时才读取目标工程的 API、board/Profile、实现模板和验证环境。

## 执行要点

1. 先还原点位，给工艺条款编号，写出“必须保持的规则”：设备关系、动作顺序、模式、控制方向、
   并行数量、已有阈值和接口。引用当前有效版本；不因一般经验覆盖 PLC 初步需求明文。
2. 从点位+原文匹配 W01–W08 及变体；异构变频/工频组追加 W09 组合卡。双泵不等于禁止并联，液位不等于排水，溶氧/压力点不等于
   KZ3 拥有 PID，泵运行不等于流量证明。不能凭一个关键词套模板。
3. 逐边界记录 MATCHED/GAP/CONFLICT/UNSUPPORTED/NOT_APPLICABLE，证据不足不得标 MATCHED。
   原文已经确定的 MATCHED 直接保留；GAP 给具体建议和影响；CONFLICT 引用冲突条款与最小修正；
   UNSUPPORTED 写缺少的信号/接口或平台能力，不静默删除要求或编造点位。
4. 只将 GAP 和需要裁决的冲突形成少量稳定决策卡；不重新询问全部工艺，不要求用户画状态机。
   没有新增缺口时直接汇总匹配结果。已有授权能覆盖的软件细化直接记录依据；会改变已定工艺的建议
   作为变更另列，未接受前保持原文和未决状态。
5. 交付原要求保留表、边界差异表、完整需求草案和验收场景。每条选定边界映射到 TABLE_CONTROL_V1
   的域和 required_scenarios；候选建议沿用 decisions，只有已有明文/明确采纳才填写 accepted。
6. 冻结前确认所选分支的输入序列与输出断言唯一；不适用案例和分支记录理由，避免以“全部不适用”漏审。
   实现和验证都按同一组边界 ID 回查 PLC 初步需求原文，防止用默认案例改写业务。

## 对用户的表达

建议：“原文已明确格栅与压榨机同步、手动独立，这两项保持。尚未说明自动运行时压榨机故障的影响；
建议此时停对应上游并报警，故障清除后按既定恢复方式处理。是否采纳这项补充？”

不要把“行业一般先开下游”变成已确定的先后启动；也不要在已有“手动独立”时重复提出三机手动联锁。
保护冲突需给出具体后果和最小变更，不能用“案例更安全”替代工程分析。

## 需求产物的追溯格式

`原文条款/点位 → 案例变体/边界 ID → 匹配状态 → 保留内容 → 补充规则与影响 → 采纳依据 → 测试场景`。
所有关键规则同时进入正常/故障/恢复状态表；这里的差异表用于追溯，不是另一份互相竞争的需求书。
