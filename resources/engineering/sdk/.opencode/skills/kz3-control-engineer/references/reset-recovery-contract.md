# 故障复位与重新投入契约

复位允许使故障设备恢复可用。不能把“复位只清故障”理解为绝对禁止阶段、监督计时或重投许可变化。
逐台冻结恢复策略和可修改字段白名单，测试实际结果；既有模板须按该策略评价。

默认 `RESET_TO_READY`：根因解除、所需输入质量 GOOD、真实反馈符合安全条件时，清本机允许的故障记录，
允许本机 FAULT → READY，清本机故障监督计时，解除本机故障导致的重投禁止，并丢弃旧启动意图。
这可以修改冻结表明确列出的本机阶段、定时基准、重启许可和失效请求；不是禁止所有控制状态改变。
健康运行时重复复位必须幂等，不得仅因复位额外断开或建立输出。

| 恢复方式 | 复位后行为 | 必须验证 |
|---|---|---|
| RESET_TO_READY + FRESH_START（缺省） | 手动等待新的启动；自动等待重新投入事件。恢复可用，但复位当拍不启动 | 旧命令消耗；复位+启动同拍复位优先；下一拍新启动/重投成功 |
| RESET_TO_READY + CURRENT_AUTO_DEMAND | 经工艺明确采用，复位拍禁止新启动，随后从当前有效自动需求重新仲裁 | 不是复用历史请求；根因解除/质量/owner/参数齐备；明确重新计时还是保留 |
| RESET_RECORD_ONLY | 清历史记录，保持原工艺阶段；独立重投路径恢复 | 符合需要保留阶段的顺控，根因仍在不能清有效故障 |

`CURRENT_AUTO_DEMAND` 不是所有设备的默认值，也不意味着所有自动故障都能自动消除。多步工艺、阀组、
正反转或下游仍未停稳时必须根据实际反馈选择安全重入点，禁止恢复历史步号直接继续。
本机恢复不复位共享工艺、他机阶段/延停来源/计时/许可。共享恢复另设明确 owner 与采用依据。

始终禁止：清原始故障 DI/急停或平台存储故障；把坏质量改成 GOOD；改参数、模式、累计运行时间；
复位分支直接写物理输出；清他机故障；通过清锁存绕过仍存在的根因。最终输出由统一正常仲裁和保护产生。
故障总量每拍重汇总，活动根因保持。运行/停止反馈条件按对应故障分别判断，不一律要求全部反馈为 false。

必要反例：根因仍在复位、坏质量复位、健康运行复位、双命令同拍、两设备同时复位、单台故障恢复、
复位后新启动成功、持续自动需求、过期启动不能恢复，以及共享延停不串扰。检查白名单内允许变化和
白名单外必须保持的快照；不要把“所有状态一律不变”当作通过条件。
