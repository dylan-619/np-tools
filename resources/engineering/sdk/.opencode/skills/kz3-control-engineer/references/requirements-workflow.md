# STM32-Logic 需求澄清工作流

先按 [点位表到控制代码](table-to-control.md) 的默认继承与加载策略执行。
本文的建议卡/确认仅用于新增实质工艺分歧；已经确定的共性不再请用户采纳。
首轮先完成控制模型，落盘/冻结才读取对应契约与门禁，不递归加载全部参考资料。

目标是从现场点位和关键目标主动形成完整的工艺控制需求，能够唯一约束配置、C 逻辑和测试。
用户无需先提供专业方案；按 [工艺设计与方案选择](engineer-intake.md#工艺设计与方案选择) 完成建议，
再用 [工艺边界匹配](plc-boundary-matching.md) 核对遗漏。有效约束保留，有缺陷的要求说明影响并提出修订。

## 工作方法

先执行 [少量确认的需求补全协议](recommendation-first-design.md)：主动建立控制关系与正常/异常/恢复
路径，把软件细化、工艺裁决和调试证据分开处理；用户只选择实质业务分歧。

读取 [端到端交付契约](end-to-end-delivery.md)。需求阶段就给出安全/稳定性与 HIL 的验收候选：最大允许
反应时间、持续/循环负载、通信/掉电恢复、禁止动作及测量方式；数值取自已有证据，缺失时给有依据的
推荐供确认或标待补。实现行为所需的安全时限未定阻止冻结；纯硬件验收条件待齐不阻止满足门禁的软件
阶段，但阻止相应硬件放行。主 Agent 的完整交付范围持续有效，需求文件不是完整任务的终点。

1. 读取适用工作区规则和本技能的 [PLC 工程建议与经典场景目录](plc-engineering-recommendations.md)、
   [PLC 边界匹配](plc-boundary-matching.md)及命中的内置案例。已有目标工程时再读其开发指南和有效需求；
   无工程仍可独立设计控制方案与补全需求。案例提供结构和边界参考，不继承其端子、站号、极性和安全值。
2. 阅读 [白话沟通与点位解析](plain-language-and-point-parsing.md)。先把用户原话复述成简短控制流程；
   用户给出点位或配置文件时，必须先读文件再提问。
3. 联合解析点位的 `name`、`description`、`type`、`direction`、`bind`、质量和安全属性，提出启停控制、
   运行反馈、故障、频率反馈等角色映射。描述与结构字段冲突或同一角色有多个候选时，不自动选择。
   A11 标准板在固件/板型未变时，直接依据 `application/io_definitions` 和底层映射记录 DI 低有效且
   逻辑 `true` 表示业务状态成立、DO 高有效且 `false` 为软件安全目标；不逐路向用户确认相同极性。
4. 给原工艺条款编号，匹配主/辅助案例及变体，记录已明确、缺口、冲突、能力不足或不适用。
   已明确项保持；只为缺口输出“建议补充、依据、工艺影响、替代、验收”的卡。用户授权软件细化可
   沿用，但不覆盖明文，不补写物理事实/数值。完整交付原文保留表和边界差异表。
5. 从用户材料中提取确定信息，按 [完整性门禁](completeness-gate.md) 建立内部矩阵，并同步维护
   [机器可读需求契约](requirements-contract.md)。每条结论标注
   `已确认`、`证据待补` 或 `候选默认`；默认不把整张矩阵展示给用户。
   多设备先用 [PLC 设备单体与共享工艺归属契约](device-ownership-contract.md) 列全设备 owner 表和
   共享工艺/安全范围表，再判定单体命令、模式、输出、故障、计时、参数与真正共用的测量和调度；
   缺一台或归属不清时保持 DRAFT，不靠后续补丁逐项修补。
   同时从所有输入点逐台识别真实运行反馈；不按设备名称排除，自动列出“反馈 → runtime 名称 →
   只读 `*_RT_S` → 本机 `*_RT_CLR`”北向映射；内部 `clear_pending` 只用于逻辑和完成测试，
   不新增 `*_RT_PND` 北向点位。即使只做采集或原文只要求运行状态也适用。
   运行反馈没有对应累计、或累计没有配套清零与完成判据，均是需求缺口，
   不等用户单独提出；为这些设备加入 `RUNTIME_PERSISTENCE` 验收场景，超过 16 个或既有保持槽位
   冲突时列为设计阻塞。
6. 根据用词提出 parameter、command 和 state 候选，并用白话说明推荐分类及理由。用户只需确认业务
   用途；不要把 schema、quality、one-shot 或状态机设计作为开放问题交给用户。
7. 将未知项按 `ADOPTABLE_RECOMMENDATION`、`CONFIRM_RECOMMENDATION`、`EVIDENCE_BLOCKER` 分类。
   前两类必须先给首选答案和影响；未采纳的业务决策和缺失的物理证据均阻止冻结，但不阻止交付 DRAFT。
   使用稳定编号的决策卡，一次最多集中确认三组相关决策，不因用户不回答就重新列同一批问题。
   多台设备只写“手动”时，直接形成一张整组建议卡：逐台独立控制，手动/自动请求分域，除共用安全
   保护外操作一台不影响其他设备；直接沿用已定共性，不逐台询问。手动联动只能来自 PLC 初步需求明文或
   用户对这张建议卡的修改，不能从自动顺控、轮换、PID、加减机或联停逻辑推导。
   多台受控设备有自动业务时，同一张卡还要建议每台设备独立自动选择；自动选泵/轮换/联动仅从已选
   自动且可用的设备中取候选。逐台列出选择字段与需求来源，给出候选不足、联动依赖未选自动、退出/
   重入自动的首选业务结果，仅对新增实质工艺分歧集中确认，不反复询问每一台。组级自动使能可以保留为附加许可，
   但不能代替逐台自动选择；若与 PLC 初步需求明文或既有接口冲突，保留差异供裁决。
   缺少联动例外时首选建议：依赖的下游未选自动即阻止上游自动启动并报告联动受阻，不能因下游手动
   运行就擅自认定自动联动满足。逐台上电默认自动状态与模式保持策略也须冻结，未知时建议禁止自动
   恢复，不凭旧选择状态直接重启；切回手动不复用旧手动启动请求，重入自动须重新使能。若要求无扰
   连续运行，单独给出条件和测试，不静默沿用该默认。
   多设备故障复位同样给一张整组建议卡：每台独立复位本机软件故障，其他设备不受影响，客观故障
   仍在时本机总故障不清；直接沿用已定共性，不逐台追问。确有系统级软件故障再单列系统复位
   范围；既有 `SYS_RST` 不能未经迁移决策直接改成逐台命令。
   若自动控制按运行/停止时长循环或定时轮换，在同一整组建议卡逐台列出可调运行时长与停止时长，
   不能因同组时长相同就合并成一对全局参数。优先给分钟单位 `*_RUN_M/*_STP_M`；PLC 初步需求已定其他
   单位则保留其语义并统一命名。对每台写明时长来源/初值、有效范围、零值/非法值禁用、运行与停止
   计时起点、切换/故障中断和在线修改生效规则；没有现场数值时标调试占位，不反复让用户猜时长。
8. 需求出现“其他采集器/业务机/上级写入当前值”时读取
   [外部实时输入契约](external-input-contract.md)，提出 `external_input` 角色映射；冻结生产者、唯一写入
   owner、发送周期/抖动、类型/单位/范围、时效、首次报文、断流、恢复和再启动，不把它误归为普通参数。
9. 将控制规则写成可执行的 Given/When/Then，给每个场景分配稳定大写 ASCII ID，覆盖正常、冲突、
   坏质量、故障、STOP/Reset、超时、恢复和时间边界，并填入
   `verification.required_scenarios`。
   每台受控设备列出硬件故障反馈、设备级软件故障、只读总故障与独立故障复位；分别给出硬件故障、
   软件故障、两者同时存在与本机复位后硬件故障仍在的总故障预期。复位一台不得清除其他设备的
   软件故障或改变其总故障；无硬件故障反馈时明记缺失，不虚构输入。多设备项目声明
   `PER_DEVICE_FAULT_RESET`，追加 `DEVICE_RESET_OWNERSHIP`、`DEVICE_RESET_ISOLATION`。
   对启停设备/开关阀按 [通用反馈故障契约](device-ownership-contract.md) 逐台列出适用故障：
   有启动/停止或开/关到位反馈时监督相应超时；只有独立真实运行反馈且存在本机持续运行目标时，
   才监督已确认运行后的滚动反馈丢失，继电器设备未指定时为 `5000 ms`；实际硬接故障反馈存在时才列入。
   只有开、关到位反馈的阀门只做开阀、关阀超时，不默认增加到位丢失或运行累计。
   未指定反馈时限直接沿用契约默认表（继电器设备启动 5 秒、停止 30 秒、运行丢失 5 秒；阀开/关各
   120 秒），正文记录数值和已定共性来源，不再次确认；明确值优先。已有设备故障输出
   可复用但须核对覆盖范围。验证至少分开正常到位、到时前/到时、反馈恢复、坏质量、硬接故障及
   本机复位后客观故障仍在，并明确故障处置和恢复不误启。
   多设备自动项目声明 `PER_DEVICE_AUTO`，追加 `AUTO_SELECTION`、`AUTO_POOL_ELIGIBILITY`、
   `AUTO_MODE_ISOLATION`；逐台模式表和候选/容量边界必须能追溯到 Given/When/Then。
   自动运行/停止周期项目另声明 `TIMED_AUTO_CYCLE`，逐台参数、到时边界、实例隔离和在线变更
   对应 `CYCLE_PER_DEVICE_PARAMETERS`、`CYCLE_TIME_BOUNDARY`、`CYCLE_INSTANCE_ISOLATION`、
   `CYCLE_PARAMETER_UPDATE`，不能只用一台设备的测试代表全组。
10. 用户要求落盘或进入完整自动流程时，使用 [项目需求模板](../assets/project-requirements-template.md) 创建
   或更新目标项目的 `README.md`。新建未冻结项目可使用“需求草案”目录；已有项目保持原目录，并明确草案不登记、不构建、不驱动硬件；
   阻塞项必须保留，不能用经验值补齐。无目标工程时直接写用户指定文档或当前工作区 works，不创建 application/projects。
11. 按 [北向 HMI 点表契约](northbound-contract.md) 建立 HMI 字段白名单、排除项和缩写词典；不得把内部
   中间量默认发布。需求阶段就固定“中文业务语义 → 统一短名 → bind”映射，后续 README、YAML、
    生成点表和交付不得换用同义缩写。修改已有项目时保持已有地址和顺序，不得通过重排制造地址漂移。
    对已接线且配置工程量程的 AI 仪表，逐路把换算后工程值列入必需的只读北向测量字段，记录单位和
    无效显示依据；原始电流/码默认不重复发布。
12. 独立文档使用 `verify_project.py --requirements-file <文件> --require-engineering-review`，冻结追加
    `--require-frozen`；该模式只检查文档。工程内需求运行 `verify_project.py <项目目录> --requirements-only --require-engineering-review`；准备冻结时运行
    `--requirements-only --require-frozen --require-engineering-review`。后者通过后才输出“冻结需求摘要”，包含需求版本、证据、项目
    身份、I/O、变量、状态机、优先级、安全
    策略、北向契约和验收矩阵。`AUTO_PROJECT` 模式直接进入生成；用户明确只整理需求时停在需求交付。

## 边界

表格输入按 [点表与简短工艺说明转需求](table-input-engineering.md) 还原模块归属、备用点和原文依据。
第一次输入即形成完整草案及推荐选项；新草案维护 `TABLE_CONTROL_V1` 工程表，检查时追加
`--require-engineering-review`。状态未冻结只阻止可运行源生成，不阻止需求文档交付。

- 物理输出请求、模块寄存器回读和真实设备运行反馈是三个不同概念。
- `command` 是 one-shot；跨扫描目标应进入 `state` 或已声明 parameter。
- 点位 `description` 可用于识别业务角色，但不能证明端子、电平、量程、安全值或真实反馈语义；结构字段
  与描述冲突时以“待确认”处理。
- 北向采用显式 HMI 白名单；已有地址兼容性优先，删除、改址或重排必须单独确认。
- 普通 state/Timer/Counter/PID 不掉电保持；parameter 缺省易失，只有显式 `persistent: true` 时才由参数
  store 掉电保存，并需冻结恢复策略。设备运行时间必须采用认证
  `T05_RUNTIME_COUNTER_USAGE` 和声明式 `runtime_counters`。启动次数、故障时长、班次/月报等未认证
  统计标记 `CUSTOM_REVIEW_REQUIRED`，不能冒充已有掉电保持能力。
- 每台受控设备都定义独立 one-shot 故障复位，默认 `M1_RST -> command.m1_reset_faults` 等；
  单设备既有 `command.reset_faults` 可保留。它只清本机需求列明的软件故障点位/锁存，不清他机、急停、
  故障 DI、坏质量、仍为 true 的运行反馈或平台存储故障。按恢复契约允许白名单内本机阶段、监督计时、重投许可恢复 READY，丢弃旧启动；不得直接写物理输出，不改模式、参数或 runtime。自动恢复方式另行冻结。
  系统级故障需要清除时另立系统专属范围，不用全局命令扇出替代设备复位；既有全局点位保留兼容评估。
- 软件不得替代必须由硬件实现的急停或保护。无法判断现场安全设计时直说“我不知道（I don't know）”，
  列出所需原理图、手册或实测证据。
- “需要确认”不等于“让用户从零设计”。除证据阻塞项外，每个问题都必须附推荐答案、理由和不采纳时的
  主要影响；用户不熟悉 PLC 时，以其能判断的工艺结果进行确认。
- 需求阶段的完成条件是需求可冻结，不是代码已生成。是否继续生成由用户的原始授权决定。
- `confirmations` 只能反映正文已有证据的结论；脚本通过不能替代工程师复核点位来源、安全值来源和用户
  决策，禁止为消除错误而把未知项直接改成 `true`。
